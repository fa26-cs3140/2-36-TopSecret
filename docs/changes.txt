CHANGE NOTES - Homework 6

Architecture: Model-View-Controller (team)
  - Classes are organized into three packages:
      model       data and storage (Agent, Brief, Facility, Mission, ModelDatabase,
                  Message, SqliteMessageStore, UserAccount, CipheredUserStore,
                  AuditLog, SqliteAuditLog, SqliteMissionStore, Access, Cipher, ...)
      view        what the user sees (HtmlView, WebPages, Homework5Menu,
                  MissionMenu, MessageMenu, AssignmentMenu, AccessMenu, UserInterface)
      controller  input and flow (WebController, LoginHandler, AccountManager,
                  ProgramControl)
  - TopSecret (the program's entry point) stays outside the packages so
    "java TopSecret", "./gradlew run", and the jar work unchanged.
  - Tests are in the same package as the class they test.

Web view (Team Member B, control)
  - "java -jar build/libs/TopSecret.jar -web" (or ./gradlew run --args="-web")
    starts an HTTP server at http://localhost:3002/. Without -web the program
    runs in the terminal as before.
  - The web view will not start until a user account exists.
  - A login form checks the username and password. Wrong credentials show an
    error. Correct ones get a session cookie (HttpOnly, no expiry date, so it
    ends when the browser closes). Every page except the login page needs it.
  - Pages: Home, Briefs, Agents, Facilities, Missions, Audit Log (admins only),
    and Logout. The web view is read only.
  - New classes: controller.WebController, view.WebPages.

HTML view (Team Member C, view)
  - view.HtmlView wraps the same data shown in the terminal in plain HTML
    tables and lists (no CSS, no JavaScript), using one page template.
  - Wireframes: docs/Wireframes.pdf.

Missions and joint operations (Team Member A, model)
  - A mission is run by one facility, agents from any facility can be assigned
    to many missions, and a mission has zero or more briefs.
  - Terminal: "4. Missions and Assignments" (admins) lists missions, creates a
    mission, assigns or removes agents, and attaches briefs. Changes are audited.
  - New table: mission_briefs. See docs/schema.txt and docs/UML_ERD.pdf.
  - New class: view.AssignmentMenu.

Messages for agents (Team Member D)
  - New "3. Messages" option in the terminal main menu (send a message to an
    agent, read my messages). At login, users with messages see a notice.
  - A message is read by the user whose username matches the agent's name,
    ignoring case. Nobody else can see it. Admin access is not needed.
  - New messages table linked to agents (ON DELETE CASCADE). See docs/messages.txt.
  - New classes: Message, MessageStore, SqliteMessageStore, MessageMenu.
  - Sending and reading messages are recorded in the audit log.

CHANGE NOTES - Homework 5

Homework 4 -> Homework 5

Program behavior
  - After login, a top menu offers the existing mission menu or the Homework 5
    records menu (Mission Briefs, Agents, Facilities).
  - Each record type can be listed, read, added, updated, and deleted. New and
    updated items show up in the list right away.
  - Deletes that would leave orphaned data are refused with a clear message.
  - Sample facilities, agents, and briefs are loaded from database/*.tsv on first run.
  - Multiple user accounts in a ciphered users.cip (replaces credentials.cip).
    The first account is an admin. Admins add users by username only; the new
    user creates their own password at first login.
  - Passwords need at least 5 characters with uppercase and lowercase letters.
    Usernames need at least 3 characters: letters, numbers, - and _.
  - Access levels: standard users can only read. Admins can add, update, delete,
    add users, view the audit log, and promote/demote other users (not themselves).
    Users never see options they cannot use.
  - Audit log in the database: every read, create, update, and delete, with who and when.

New classes
  - Brief, Agent, Facility, ModelDatabase (C)
  - Homework5Menu (B)
  - UserAccount, UserStore, CipheredUserStore, AccountManager (incl. setAdmin for A),
    AuditLog, AuditEntry, SqliteAuditLog (D)

Removed
  - CredentialManager and credentials.cip (single-user login, replaced by multiple accounts)

Testing
  - Mockito is used in unit tests (mocked UserStore and AuditLog).
  - Every class has unit tests; integration tests are named after the classes
    they connect, e.g. Homework5MenuSqliteAuditLogTest, AccountManagerCipheredUserStoreTest.

CHANGE NOTES - Homework 4

Homework 3 -> Homework 4

Program behavior
  - The program is now interactive. After login it shows a menu (list, read,
    search, exit) and keeps running until the agent chooses Exit.
  - A login is required. On the first run the program asks the agent to
    create a username and password, saves them ciphered in credentials.cip,
    and exits. Later runs ask for the username and password.
  - "java TopSecret --change-password" changes the password after the new
    password is entered twice.
  - Mission briefs now come from a SQLite database instead of the text files
    in data/. The database is created in database/missions.db on first run
    and loaded from database/mission_briefs.tsv.

New classes
  - Mission                   one mission record (id, title, brief, date)
  - MissionStore (interface)  how the rest of the system reads missions
  - SqliteMissionStore        the only class that accesses the database (A)
  - CredentialManager         reads, writes, and checks credentials.cip (B)
  - LoginHandler              login, first-run setup, password change (B)
  - MissionSearch (interface) and MissionSearchService  search feature (C)
  - MissionRepository (interface) and MissionMenu  interactive menu (D)

Interfaces
  - MissionStore extends MissionRepository and MissionSearch, so the menu
    works with any store and never touches the database directly.

Kept from Homework 3
  - Cipher is reused to decipher the credential file.
  - FileHandler, ProgramControl, and UserInterface remain with their tests.

Docs added
  - schema.txt (database table), team.txt, uml_design.png, this file.
